## 外部工具验证了什么

固定使用 Sierra `tau2-bench` 提交 `672227c6b6676edc20d57ea53b7000262aae77b9` 的 `EnvironmentEvaluator`，开启 `strict_replay=True`。该工具允许不同动作序列达到相同数据库目标；我们按已登记的案例标签构造独立参考动作。方法定义见[固定版本的官方评价文档](https://github.com/sierra-research/tau2-bench/blob/672227c6b6676edc20d57ea53b7000262aae77b9/docs/evaluation.md)。

预测环境从原初始 SQLite 副本重新执行，使用该次原有 v5/v6 类和模拟时刻。实际覆盖读取订单 188 次、读取完整商品资料 174 次、读取运输事件 140 次、读取提案 145 次、生成修订 108 次。调用真实工具并重建观察状态；没有返回保存的结果来代替执行。案例没有调用候选检索、选择变体或确认交易，不能由本轮推断这些路径也获得了外部回放覆盖。

所有 755 次调用的原生 JSON 返回类型和值逐项一致。metadata、inventory、drafts、approvals、proposals、transport_events、confirmations 七张表的全部行与字段也一致，包括所有提案版本、引用关系、库存与规则版本、批准、确认和业务时间。仅排除 traces 审计表；实际工具返回另从预测库的 traces 表逐项独立读取核对。

108 次实际创建保留记录中的随机提案 UUID，以支持后续按 ID 查阅。注入仅限 UUID 工厂；路线、价格、库存、状态和版本由程序重算。参考环境使用独立 UUID，目标比较按“所属订单与版本”一致映射，保留前后引用。参考路线由同一冻结规划器生成，因此目标相等不证明全局最优；路线可行性另有[原独立审计](evidence/apparel_reliability_audit_20260909.json)。完整规则见[本轮协议](../research/APPAREL_TAU_REPLAY_PROTOCOL.md)。

## 两个不能被“全部通过”掩盖的案例

- `RL-09-1 / v5_coordinator`：数据库已经形成正确的新提案，但最终回答在必需引用和整理结果时耗尽调用额度。它的回放和数据库目标通过，原任务仍按 `call_limit` 失败保留；不能据此把协调员的 23/24 改成 24/24。
- `RL-02-0 / v5_on_demand`：第 7 条观察查询了错误提案 ID，工具返回 `Unknown proposal in this order`。这次错误同样重新执行并准确复现，没有从分母中删除；原轨迹后续恢复并通过任务验收。

## 适配器反例与独立复核

13 项测试涵盖真实轨迹、合法业务错误、只读/写入结果篡改、跨订单错误 ID、未记录的非选中 SKU 库存变化、遗漏写入、额外合法读取、创建 ID 复用、版本引用破坏、数字字符串混淆，以及模型/GPU 禁用哨兵。它们是程序验证案例，不计入 Agent 的统计分母。

开发时首轮为 12 通过、1 失败：测试原以为上游保留 JSON 数值类型；查阅源码发现它将数值与布尔值转成字符串，故将类型反例改成“数值 2 被写成字符串 2”。最终 13 项全部通过。适配器补充原生 JSON 类型校验，可以识别这个上游序列化会掩盖的问题；未修改上游或业务代码。两次测试记录均保留。[首轮](evidence/apparel_tau_bridge_tests_20260909.xml)、[最终测试](evidence/apparel_tau_bridge_final_tests_20260909.xml)。

独立复核脚本只使用 Python 标准库，从预测 SQLite 的实际 `agent_tool` 轨迹、七张业务表和原始记录重新核对，不调用适配器或模型。核对 2,623 个文件散列、755 条完整返回、108 次创建及对象关系、六组计数、参考动作来源和账本，全部通过。[审计结果](evidence/apparel_tau_replay_audit_20260909.json)。

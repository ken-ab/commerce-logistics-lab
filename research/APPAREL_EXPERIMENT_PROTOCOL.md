# 固定业务上的执行策略对照 · v1

登记前先完成订单、运输、界面开发和开发试跑。验证与测试都使用此处登记的同一业务和评分版本。测试结果不用于修改提示、案例期望或评分规则。Finance-Agent 不参与。

## 研究问题与组别

对同一服装订单与跨境履约任务，增加协调和专家调用是否提高任务可靠性，其费用和时延代价是多少？

三组均使用 gpt-5.6-luna、既有核验过的服务配置、相同 37 条公开来源服装变体、同一单仓走廊、所有业务工具的相同实现、1536 completion-token 上限及 low reasoning 配置。全任务上限 12 次模型调用、32 次业务工具调用；每次专家委派最多使用 4 次模型调用，计入全任务额度。没有隐式网络重试。

- 单 Agent：直接使用全部业务工具。
- 协调员加专家：协调员调用商品、物流或服务专家，再汇总结果。协调员本身仅有委派和完成工具；专家拥有与单 Agent 一样的业务工具集合。这一职责和上下文差异就是研究的编排处理。
- 按需委派：执行者默认可直接处理，记录依据请求或已观察状态作出的直接处理/委派理由；可以根据新状态改变选择。专家不能继续委派，委派理由和看到的 observation ID 均保留。

三组的业务能力总集合一致。专家提示、职责、上下文和多次往返属于编排差异，不宣称这些差异已被单独消融。所有工具按返回顺序串行执行，不比较专家并行加速。

## 数据与顺序

开发资料查询和流程样例使用 3 个特定目标 SKU。另选 8 个目标 SKU 构造 18 个验证任务，剩余 26 个目标 SKU 构造 108 个最终任务，分为 9 个业务类型、每类 12 个。整个目录仍可搜索，所以“目标 SKU 不重合”不等于模型从未看到测试商品。所有案例均为开发者编写的模拟业务任务，不是实际商家订单或外部公开基准的测试分数。

每个案例先建立一次初始数据库，再用 SQLite backup 克隆到三组；初始订单 ID、提案 ID、库存、具体替代批准和事件相同。模型只接收任务正文、已确认订单和工具返回；分组标签、期望结果与评分代码不进入提示。模拟时钟固定，取消/延迟/错过班次根据该时钟判断。初始状态摘要和源文件 SHA-256 均保存。

先完成 18×3=54 次验证，再开展 108×3=324 次最终运行。每个任务/策略只运行一次，不挑选最好答案、不删除失败、不因测试结果不满意补样本。任务次序和各案例的策略次序使用固定随机种子。最多 3 个独立运行并发，三组交错安排，记录实际时延。一次运行中断时保留账本预留和已写轨迹，不自动重跑同一任务。

## 预先定义指标

| 指标 | 定义与边界 |
|---|---|
| Task Accuracy / 任务完成率（主指标） | 业务状态、候选约束、必要版本/动作均符合独立案例期望，且要求的来源字段有引用。分母包含所有登记运行。它不是商品检索 NDCG 或分类 Accuracy。 |
| Business Success | 上述业务结果通过率，单列便于辨别“业务做对但证据未给全”。 |
| Constraint Violation | 擅改需求/批准/确认/库存、改写历史提案，或把当前无效订单/路线建议为 ready 的运行占比。程序拦住的违规工具请求另列，不冒充已经执行的违规。 |
| Evidence Coverage | 是否引用本任务需要的字段，例如问题代码、替代差异、当前提案费用和到达时间。最后的字段值由宿主从真实工具返回中直接提取；引用修复也计成本。该指标不是对自由理由中每句自然语言的事实评审。 |
| Avg Cost（CNY） | 每个登记任务计入共享账本的费用平均值，包含未知结算调用的完整预留；另列已结算 token 估算。不是供应商账单。 |
| Avg / P95 Latency | Agent 开始处理至返回/失败的墙钟时间，包含工具、协作、报告修复；不含创建实验初始数据和事后评分。相同最大并发条件，仍可能有网络/服务排队噪声。 |
| Calls / Tokens / API Success | 全部根节点及专家模型调用、业务工具调用、输入/输出 token、成功 API 调用占比；失败调用 token 未知时不填 0 作为实际 token。 |
| Delegation | 委派次数、直接/委派理由和按任务类型的比例。 |

未单独测量首 token 时间和真实思考秒数；模型调用总时长不能当作思考时长。新 Agent 比较也不沿用商品检索 NDCG，否则指标与任务不匹配。

## 分析与采用规则

三组总表与 9 类任务分别报告。主指标、费用、时延按相同 case ID 配对；报告配对 bootstrap 的差异区间（10,000 次，固定种子）。同一小目录和模板下的模拟任务存在相关性，区间仅描述这套案例的不确定性，不外推所有服装商家。额外报告按目标 SKU 聚类重采样的区间，防止把同一商品的多条变体任务当成完全独立证据。

不预设“多 Agent 更好”。验证集选择用于界面默认的策略：先排除有执行约束违规的策略，再取任务完成率距验证最高值不超过 2 个百分点的组，按平均费用、平均时延选最低者。最终测试只验证该固定选择并展示三组对照；若验证选择在测试中出现实质安全问题，保留手动界面并禁用其自动建议，不用测试集反复调参。

若只是费用降低且完成率相近，称“本套任务中更节省”，不称统计等价或所有任务最佳。自由理由仅供错误分析，不纳入未定义的主观总分。

## 预算、来源与复现

预计 378 次任务约 1,500–3,000 次模型调用，开发校准估计费用 12–25 元，计入全项目累计 480 元。100 模型选型子任务已完成，仍按其原 100 元上限保存。共享账本、历史支出和不确定预留不清零。程序每次调用前按验证价格卡预留，480 元为硬限制。

方法参考 [ReAct 原论文](https://arxiv.org/abs/2210.03629) 的工具观察—行动循环；[LangChain 官方多 Agent 文档](https://docs.langchain.com/oss/python/langchain/multi-agent) 的协调、专家和上下文职责区分；[τ-Bench 官方仓库](https://github.com/sierra-research/tau2-bench) 的策略、工具、任务及轨迹评测划分。这里的 3 个具体组别、模拟案例、评分字段和预算选择规则由本项目定义，不声称照搬了已有论文的完整实验。

商品来源：[Amazon ESCI](https://github.com/amazon-science/esci-data)。款式分组、库存、销售地区和 MOQ、重量、费用、班次和事件均明确标注为研究模拟；单件包装单位也不是从标题擅自推断的真实商家规格。公开标题明确出现 2-Pack 的资料保留对应换算依据。

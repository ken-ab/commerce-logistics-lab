# Public distribution and reproduction

The supplementary `rationale-audit.zip` preserves the completed explanation-audit schedule, including invalid outputs and missing coverage. `python -m public_release.verify_results` checks its 144-case join, original inputs, group counts and study-only accounting export. Original execution-source copies are under `evidence/apparel_rationale_frozen_source/` so public adapter changes do not alter the frozen record. One private reading-provenance receipt is deliberately omitted and listed by path and hash; it is not an experiment input or model output. No paid-community source document is distributed.

The recovery runner's six raw-save failures are preserved. For any newly registered experiment, create the output directories before inference, use a fresh destination, and register the corrected runner; do not use completed historical directories as a new campaign. No schema-invalid response was truncated into a success or resampled to replace a failure.

The original experiments ran on Windows in a private working checkout. This distribution keeps the business modules, methods and original completed records; it adds `public_release/` to make the workbench and evidence verification independent of that machine's absolute paths.

## Evidence layers

1. `archives/*.zip` holds original bytes of the selected completed studies. SHA256 and member manifests are in `public_release/archives.json`. Extraction checks membership, size, hashes and destination containment, and refuses to overwrite a changed local record.
2. `public_release/research_snapshot.json` was exported after the original catalogue-agent, product-source, proposal-reliability, apparel-study and selected-ranking release gates all passed. It describes those historical experiments.
3. `public_release/release.json` identifies the distributed runtime and archives. Startup checks that manifest rather than evaluating historical absolute Windows paths. A checksum is an integrity check, not a claim that a result is scientifically correct.
4. `python -m public_release.verify_results` independently aggregates the saved business rows and reruns the published metric code over GPU ranking outputs and all model-selection stages. This requires no provider key or GPU and does not change the original scores.

One early model-selection response lost its usage fields even though its ledger entry was already settled. `selection_accounting_overlay.json` exports that one scoped correction used by the original readout. It contains aggregate usage and cost, not the private project ledger. The original response file remains unchanged.

The archives include synthetic experiment databases, tool traces, failures, fixed schedules, model identifiers, costs and token counts. They exclude the private payment ledger, account model directory, current interactive orders, credentials, CV files and paid-community materials. Some original registration fields contain historical Windows paths; these are retained as provenance, not used as paths outside this checkout.

The expanded order study, proposal study, external-framework replay and API model-selection study have different tasks and denominators. Do not sum their attempts into unique customers or reinterpret a route feasibility pass as free-text factual accuracy.

## A new experimental run

The registered outputs are immutable historical records. For a new model or strategy, use a separate checkout/output directory and a newly dated registration. Record the model endpoint, returned identifier, prices, data split, tool and policy versions before inference. Use the case builders and evaluators under `research/`; keep all first attempts and transport failures. Do not edit the archived registration or call a recovery command to regenerate an unfavourable completed result.

The primary protocols are:

- [GPU ranking](../research/RANKING_PROTOCOL.md): full official test split after instruction selection, fixed local model revision and candidate pools.
- [Apparel strategy](../research/APPAREL_EXPERIMENT_PROTOCOL.md): common tools and business world across three strategies.
- [Expanded operations](../research/APPAREL_EXPANSION_PROTOCOL.md): 72 states, 277 research variants, 216 recorded executions.
- [Proposal reliability](../research/APPAREL_RELIABILITY_PROTOCOL.md): 24 states × two versions × three strategies; three v6 interventions were combined, so this is not a single-factor ablation.
- [External-framework replay](../research/APPAREL_TAU_REPLAY_PROTOCOL.md): a project adapter over the pinned, unmodified τ framework, replaying recorded tool operations and database targets. It is not an official benchmark run or a new set of generative-agent attempts.
- [Model selection](../research/MODEL_SELECTION_100_FINAL_READOUT.md): economic configurations, explicit quality gates, score definitions, missing values and held-out paired uncertainty.

Re-running a paid model can yield different output even under the same request parameters. Reproduction here means that inputs, method, original outputs and metric calculations are inspectable; it does not promise identical remote model weights or bit-identical completions.

## Application policy scope

The portable workbench uses the same `scoped_operation_agent` factory: v6 applies only to explicit proposal review; other explicit operations retain the validated product-source policy. Custom tasks keep the existing general workflow. The archive's research world has 277 variants; the interactive workbench intentionally retains its separate 37-variant snapshot. It does not silently replace existing user order data.

Distribution-only changes defer the historical offline evaluator imports in `delivery.py`, display the configured zero budget correctly, and recognise explicit Aliyun payment errors returned as HTTP 400 in the operational provider hold. Order, inventory, approval and route algorithms are unchanged. The old registered provider code is not silently treated as if it had already handled that error.

The original reports describe the experiment status at their timestamps. Later supplementary rationale judgments and manual review belong in separate dated records; they do not replace the 216-run and 144-run operation scores.

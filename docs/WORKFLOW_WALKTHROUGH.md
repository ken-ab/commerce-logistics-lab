# 一笔服装订单怎样走到模拟确认

这个项目帮助服装商家回答两个问题：这笔订单能不能满足，以及在给定预算和交期内怎样运输。商品检查与运输规划围绕同一笔订单连接起来，客户明确要求的变化需要单独确认。

下面是一笔实际执行过的本地验收场景，使用虚构品牌、模拟库存和模拟运输班次。它检查程序的业务逻辑，不调用模型，不代表真实商户或真实发货。

客户需要20件BrandA黑色M码T恤，送往德国；9月10日备货，9月17日前到达，运费预算200美元。所有时间按UTC解释。

| 遇到的情况 | 系统实际处理 | 保留的业务约束 |
|---|---|---|
| 原商品没有库存 | 找到有20件库存的BrandB候选，明确指出品牌不同 | 尺码、颜色、数量保持；更换品牌需要客户确认 |
| 已选替代品，但还没确认 | 拒绝生成运输提案；错误的替代确认编号也被拒绝 | 选入候选不等于同意变更要求，模拟库存仍为20 |
| 客户确认了具体替代品 | 生成公路—空运—公路提案，运费173美元 | 客户原始要求保留，另存具体替代确认依据 |
| 原航班取消 | 旧提案核验失败，确认请求被拒绝；生成版本2 | 同一批准商品、200美元运费预算和原交期 |
| 版本2生成后库存降到19件 | 最终确认再次被拒绝，没有扣库存 | 先前认可替代品不豁免库存检查 |
| 库存补回20件 | 重新生成版本3，使用更新后的库存依据，再完成模拟确认 | 旧版本保留且被标为已替代 |
| 再次点击确认 | 返回相同确认编号，只存在一笔确认记录 | 库存只从20降到0一次，已确认订单禁止修改 |

航班修订把空运出发从9月10日16:00移到9月11日04:00。两版都能赶上9月12日08:00的后续公路段，因此运费仍为173美元，最终到达时间仍为9月12日20:00。这是班次发生变化但最终交期未变的情况；旧航班失效的事实仍保留。

系统对“已经确认”的重复请求返回原确认回执；它不会把这个回执解释为重新发起一次运输。对于尚未确认的提案，则始终重查当前商品、库存和运输条件。

本次只覆盖上述一条串联场景，共19次本地HTTP请求，其中包含预期的拒绝。另有两次模拟库存变化。它验证各环节在这一组合下能协同工作，不是19个独立案例、19位用户或模型成功率。历史模型实验、失败和分数均未修改。

模型在完整应用里负责理解请求、选择工具和解释结果；程序负责规格、库存、规则、路线和确认检查。一次确定性流程验收不证明模型每次都会正确调用这些工具，模型表现仍以原有独立实验为准。

目前功能边界是单仓、一个跨境运输走廊、模拟库存/规则/运输条件，支持确认前的异常修订。尚未接入支付、真实承运商订舱、真实库存或实际发货。技术资料用于解释设计和查缺陷，新增技术须服务于这条业务流程。

复核代码：[完整流程测试](../tests/test_apparel_workflow_logic.py)。在已配置依赖的项目环境中运行：

```text
python -m pytest -q tests/test_apparel_workflow_logic.py -o junit_family=xunit1 --junitxml=evidence/workflow.xml
python -m research.read_workflow_acceptance evidence/workflow.xml --output evidence/workflow.json
```

测试使用独立临时数据库，模型任务入口被替换为禁止调用的桩。它不操作用户正在使用的订单数据库，也不进行付费调用。使用新的输出文件名保存每次记录，避免覆盖旧结果。

已发布[首次验收记录](../reports/workflow_logic/acceptance.json)及[公开目录复现核对](../reports/workflow_logic/reproduction.json)。前者包含原始XML的SHA256、六个检查节点和完整19次请求响应；只将随机生成的测试对象编号替换为稳定别名，不包含本机主机名。两次执行的完整请求响应在编号归一化后相同，属于同一场景的复现，并未增加独立样本数。[导出脚本](../research/read_workflow_acceptance.py)可从新生成的XML得到同口径结果。
